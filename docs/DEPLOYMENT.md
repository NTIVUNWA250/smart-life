# Deployment

Everything here is on a free tier except the one item that has no free path
(iOS, see the last section). Nothing in this document requires a card.

| Piece | Host | What "free" actually means |
|---|---|---|
| Web (`web/`) | Cloudflare Pages | Genuinely free, unlimited bandwidth, no cold start |
| API (`backend/`) | Render - free web service | Free forever, but **sleeps after 15 min idle** |
| Database | Neon | Managed Postgres, autosuspends, wakes in ~1s |
| Android (`mobile/`) | GitHub Releases | Free APK hosting |
| iOS | - | No free path - see below |

Vercel Hobby is smoother for Next.js and would also work, but its terms are
non-commercial only; Cloudflare Pages has no such restriction. Render's free
Postgres is **not** used here because it is deleted after 30 days - Neon's free
tier has no expiry. Supabase is excluded deliberately: SRS section 2.5 requires plain
PostgreSQL with no Supabase.

Deploy in the order below. The web build bakes the API URL in at build time, so
the API has to exist first.

---

## 1 - Database (Neon)

1. Sign up at <https://neon.tech>, create a project in the region nearest you.
2. You need **two** connection strings from the Neon dashboard, not one. The
   connection dialog has a "Connection pooling" toggle; copy the string with it
   on and again with it off. They differ only by `-pooler` in the host:

```
# pooled - for the running server
DATABASE_URL="postgresql://USER:PASS@ep-xxx-pooler.REGION.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connection_limit=1"

# direct - for migrations only
DIRECT_DATABASE_URL="postgresql://USER:PASS@ep-xxx.REGION.aws.neon.tech/neondb?sslmode=require"
```

**Both are required.** Neon fronts the database with PgBouncer in transaction
mode. That is the right thing for the server, because a free Render instance
opens a new connection on every cold start. It is the wrong thing for Prisma
Migrate, which takes an advisory lock and runs DDL in a single session -
transaction pooling breaks both, so migrations must reach the database
directly. `prisma/schema.prisma` declares `directUrl` for exactly this.

The extra query parameters matter too: `sslmode=require` because Neon refuses
plaintext connections, and `pgbouncer=true&connection_limit=1` so Prisma stops
using prepared statements, which transaction pooling cannot keep across
statements.

Migrations are applied automatically on each API boot (`start:prod` runs
`prisma migrate deploy` first). You do not need to run them by hand.

To check the connection before deploying anything, put both values in
`backend/.env` and run:

```bash
npm --prefix backend run db:deploy   # applies all 10 migrations to Neon
npx --prefix backend prisma migrate status
```

To load the demo data once, after the API is up:

```bash
DATABASE_URL="<neon url>" npm --prefix backend run db:seed
```

## 2 - Secrets

Generate real values. The defaults in `.env.example` are placeholders and must
never reach production:

```bash
# JWT_ACCESS_SECRET and JWT_REFRESH_SECRET - different values, don't reuse one
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# FIELD_ENCRYPTION_KEY - must be exactly 64 hex characters
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

! **`FIELD_ENCRYPTION_KEY` is not rotatable.** It encrypts stored MoMo numbers
and approval reasons. If it is lost or changed, that data cannot be decrypted -
there is no recovery path. Save a copy somewhere durable before you deploy.

## 3 - API (Render)

`render.yaml` at the repo root is a Render blueprint, so most of this is filled
in for you.

1. Push to GitHub, then <https://dashboard.render.com> -> **New -> Blueprint** and
   point it at the repo. Render reads `render.yaml` and proposes `smartlife-api`.
2. It will ask for the values marked `sync: false`:
   - `DATABASE_URL` - Neon's **pooled** string from step 1
   - `DIRECT_DATABASE_URL` - Neon's **direct** string from step 1
   - `FIELD_ENCRYPTION_KEY` - the 64-hex value from step 2
   - `CORS_ORIGINS` - leave as `http://localhost:3000` for now; you will not
     know the real web origin until step 4
   - `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are generated by Render itself

   If `DIRECT_DATABASE_URL` is missing the build still succeeds and the server
   then fails to start, because `migrate deploy` runs before it listens. The
   Render log shows the migration erroring, not the app.
3. Deploy. When it goes live, check the health endpoint:

```bash
curl https://smartlife-api.onrender.com/health
# {"status":"ok","service":"smartlife-backend","mode":"sandbox"}
```

Your API base URL is that host plus `/api/v1`.

### The cold start

A free instance sleeps after 15 minutes with no traffic, and the next request
waits 30-60 seconds for it to wake. In a demo that reads as a broken app. Three
options, in order of honesty:

1. Load the site a minute before you present. Costs nothing, works.
2. Ping `/health` every 10 minutes from a GitHub Actions cron (free). Keeps it
   awake, and is against the spirit of the free tier if not its letter.
3. Try Koyeb's free instance instead - it does not sleep the same way.

## 4 - Web (Cloudflare Pages)

`web/next.config.mjs` sets `output: 'export'`, so `npm run build` writes plain
HTML/JS to `web/out` - no Node server involved. The design system lives at
`design-system/` outside `web/`, so the build must run from the **repo root**,
not from `web/`.

<https://dash.cloudflare.com> -> **Workers & Pages -> Create -> Pages -> Connect to
Git**, then:

| Setting | Value |
|---|---|
| Root directory | *(leave empty - repo root)* |
| Build command | `npm ci --prefix web && npm run build --prefix web` |
| Build output directory | `web/out` |
| Environment variable | `NEXT_PUBLIC_API_URL` = `https://smartlife-api.onrender.com/api/v1` |

`NEXT_PUBLIC_API_URL` is read at **build time**, not at runtime - changing it
later means triggering a rebuild, not just editing a setting.

## 5 - Close the CORS loop

Cloudflare gives you an origin like `https://smartlife-web.pages.dev`. Go back
to Render -> `smartlife-api` -> **Environment** and set:

```
CORS_ORIGINS=https://smartlife-web.pages.dev
```

Save; Render restarts the service. Until you do this the browser blocks every
API call with a CORS error, and the app will look like it cannot log in.

If you add a custom domain later, list both, comma-separated.

## 6 - Android

```bash
cd mobile
flutter build apk --release --dart-define=API_URL=https://smartlife-api.onrender.com/api/v1
```

The APK lands at `mobile/build/app/outputs/flutter-apk/app-release.apk`. Attach
it to a GitHub Release and share the link. `API_URL` is a compile-time
`dart-define` (see `mobile/lib/config.dart`), so a build pointed at localhost
cannot talk to the deployed API - always pass it.

Firebase App Distribution is also free and gives testers update notifications;
worth it if more than a couple of people are testing.

## 7 - iOS

There is no free path, and it is worth being plain about why:

- The Apple Developer Program is **$99/yr**, and TestFlight requires it.
- Building it at all requires a Mac.
- The iOS side has **no implementation** - no `MethodChannel` is registered in
  `AppDelegate.swift`, so any screen-time call would throw at runtime.

Treat iOS as out of scope until Android is proven on a real device.

- [ ] Neon project created, pooled `DATABASE_URL` copied
- [ ] `FIELD_ENCRYPTION_KEY` generated **and backed up**
- [ ] Render blueprint deployed, `/health` returns ok
- [ ] `db:seed` run once if demo data is wanted
- [ ] Cloudflare Pages built with `NEXT_PUBLIC_API_URL` set
- [ ] `CORS_ORIGINS` updated to the Pages origin
- [ ] APK built with `--dart-define=API_URL=...`

## Going live with MoMo

Deployment is independent of this - `PROVIDER_MODE=sandbox` ships a working app
with in-memory payment fakes. To switch the `momo` channel to the real MTN
sandbox, set `MOMO_SUBSCRIPTION_KEY`, `MOMO_API_USER`, `MOMO_API_KEY` and
`PROVIDER_MODE=live` in Render's environment. See `backend/.env.example` for how
to obtain them. Any missing value degrades only the `momo` channel back to its
stub; the server still boots and every other channel keeps working.
